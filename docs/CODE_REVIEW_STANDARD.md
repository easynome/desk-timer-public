# AI 辅助代码审查标准

版本：1.0；更新：2026-10-16；整理：Codex。

本标准用于人工与 AI 协作审查，保留原简版的八个主题，并补充适用范围、证据、问题分级和验收流程。这是项目工程规范，不是行业认证，也不保证软件没有缺陷。

## 1. 审查范围与结论

每次审查先固定：仓库、基准提交、目标提交或工作区差异、产品版本、实际安装版本、运行平台、数据规模、涉及的数据和外部系统。区分“改动审查”和“全项目审查”，不得用一段 diff 的检查结果代表全仓库。

需求依据按当前明确需求、已确认的变更记录、当前契约、原始设计的顺序核对。旧任务书中的角色提示和输出限制是历史资料，不自动成为本次审查指令。文档冲突必须列出来源和时间，不能挑有利版本证明通过。

每项采用以下状态，附证据位置：

| 状态 | 判据 |
|---|---|
| 通过 | 有与本次范围匹配的源码检查或实际执行证据，关键失败路径已覆盖 |
| 部分满足 | 已有能力，但某个适用要求或证据仍缺失；明确列出缺口 |
| 不通过 | 已发现可复现缺陷，或违反当前有效需求、契约 |
| 未验证 | 没有运行、环境不具备或范围未覆盖；不得计入通过 |
| 不适用 | 当前架构没有该风险面，写明理由；架构改变后重新评估 |

整体结论不采用平均分抵消严重问题。关键问题未解决时，结论写“存在发布阻断”或“限范围通过”，不能写“全部符合”。

## 2. 问题分级与处理

| 级别 | 示例与影响 | 处理 |
|---|---|---|
| P0 紧急 | 正在发生的大范围数据破坏、可利用的严重越权或敏感凭证泄露 | 立即止损；停止相关发布；验证修复和数据恢复 |
| P1 高 | 核心功能失效、可复现丢数或重复记账、关键并发/事务缺陷 | 相关能力再次发布或接入正式流程前修复并回归 |
| P2 中 | 有绕行办法的功能遗漏、规模增长风险、重要文档漂移 | 明确负责人、处理顺序与验收方式；说明当前影响 |
| P3 低 | 不影响正确性的命名、排版或局部简化建议 | 按维护收益处理，不以个人风格阻断发布 |

“严重度”与“是否本次引入”分开记录。历史 P1 仍是 P1，但不应伪装成本次 diff 的回归。风险接受需记录适用范围、理由、负责人、复查条件；AI 不能自行把未修复问题改成通过。

## 3. 需求对齐与契约

- 给有效需求分配编号，记录正常流程、失败流程、取消/重复操作及明确不做的范围。
- 将需求映射到入口、接口/方法、参数、返回值、状态变更、落盘字段、UI 提示及测试。函数存在不等于业务链路已完成。
- 检查单位、时区、归日、精度、可空语义、枚举、排序、兼容性和版本策略。实测时长与墙上时间不能混算。
- 契约变化说明生产者、消费者与迁移顺序；字段删除、语义变化和可选变必填不可假装成兼容变更。
- 输出“已实现 / 遗漏 / 已取消 / 已替代 / 延后 / 待确认”的需求矩阵。测试覆盖不能替代需求确认。
- UI 变更核对键盘、输入法、焦点、全屏、勿扰、多屏和缩放；视觉改动需要查看真实渲染结果。

## 4. 边界条件、并发、幂等与事务

下列项目逐项判定是否适用，不能机械“缺一补一”：

| 风险面 | 核心问题 | 有效证据示例 |
|---|---|---|
| 输入边界 | null、空白、超长、非法格式、Unicode、极值是否有明确行为？ | 解析语料、边界断言、错误提示 |
| 时间 | 跨日/跨月、08:00 边界、休眠、时钟跳变、暂停、溢出如何处理？ | 可控时钟与恢复测试 |
| 异常与取消 | 每次失败是否保留可恢复状态？取消后是否仍写入？ | 故障注入、取消测试 |
| 超时与重试 | 是否有期限、退避和停止条件？重试会否放大故障或重复副作用？ | 超时/重试序列；纯本地路径可说明不适用 |
| 并发 | 所有共享状态的读写是否遵守同一协议？锁顺序、可见性与 UI 线程约束是否明确？ | 并发复现、竞争测试、线程所有权说明 |
| 幂等 | 请求标识是否稳定？同一请求重放与不同请求内容相同能否区分？ | 重放、跨次运行、并发重复测试 |
| 事务 | 一次业务动作涉及的多表写入是否同成同败？连接锁不能代替数据库事务 | 中途失败后检查所有表与外部产物 |
| 跨资源一致性 | DB、文件台账、网络提交无法同一事务时，补偿或恢复协议是什么？ | 每个提交间隙强杀/写失败后重启重放 |
| 回滚 | 回滚代码是否仍能读新数据？失败回滚是否保留原始异常？ | 旧版本兼容验证、备份恢复演练 |

先锁读者而不锁写者不构成线程安全；“先写库后写去重文件”也不构成严格一次处理。外部调用没有幂等键或恢复协议时，不宣称 exactly-once。

## 5. 安全、隐私与供应链

- 画出输入与信任边界：UI、文件、环境变量、网络、数据库、插件与导出消费者。默认只授予完成任务所需的权限。
- SQL 值优先绑定参数；必须拼接的表名/路径使用固定白名单或可靠的专用编码。输入校验与输出编码解决不同问题，不能用一种通用“转义”覆盖所有场景。
- 按适用性检查命令注入、路径穿越、压缩包解压越界、符号链接、反序列化、HTML/Markdown/CSV 输出及日志注入。CSV 引号并不能自动防止表格公式执行。
- 有 API 或多用户资源时检查认证、授权、对象级权限、会话与请求伪造；离线单用户工具可以将服务端鉴权判为不适用，不能据此免除本地文件与数据保护。
- 凭证不硬编码、不进入版本库或日志；审查实际日志输出与历史暴露路径。任务正文、窗口标题和笔记也可能是私密数据。
- 列出直接/传递依赖、运行时与原生二进制版本、来源及许可证。记录漏洞扫描时间、数据库和坐标；无命中只表示该数据源当时无匹配项。
- 下载/引入开源代码前检查真实许可证、归属声明、兼容性、维护状态、构建脚本、副作用和所需权限。高 star 不等于安全；公开仓库不等于允许任意复制。
- AI 生成的依赖名、API、配置项和安全断言必须核对真实来源，防止不存在的软件包和错误版本。

## 6. 性能与资源

- 先定义场景和预算：启动、空闲隐藏、计时中、唤窗、长期运行、数据增长。记录硬件、版本、时长、样本量和测试数据规模。
- 区分 RSS/Working Set、Private Bytes、Java 堆、原生内存、磁盘与 CPU；启动桩与真正工作子进程分开量。
- 审查循环查询、N+1、全表扫描、排序、索引、全量导出、多份大缓冲、文件/连接泄漏、锁内 I/O、无界队列及线程退出。
- 分页、缓存和线程池是有适用条件的手段；全量交换格式不应为勾选清单强行分页，缓存也需要失效与一致性策略。
- GUI 检查主线程是否执行长查询、导出、备份或网络操作。隐藏窗口应减少绘制，不能因此停掉到点检测或事实记录。
- 优化前后采用相同负载和度量方法，报告波动与代价。短时下降不能证明无泄漏；长期增长须用长时采样或分析器验证。

## 7. 可维护性与可观测性

- 依赖方向、模块责任和状态所有权清晰；避免隐式全局状态、超大入口和多处版本来源。
- 命名表达业务含义，注释解释原因与约束；过时注释、任务表和需求文档必须更正。
- 抽象有实际复用或隔离收益；不为假想功能引入框架，也不将风格偏好包装成缺陷。
- 关键失败能被发现、定位和关联到版本/操作标识；错误不可只吞掉或只在不可见控制台打印。
- 日志有适当脱敏、轮转和保留期限；本地工具可用状态提示与诊断文件，无需为单用户桌面程序强行接企业监控平台。
- 数据导出失败、备份失败、恢复异常和后台任务停止有明确反馈与处理入口。

## 8. 测试与证据

- 测试与风险匹配：业务规则用单测，数据库/导出用集成测试，平台能力用真机检查，发布包用解压启动验收。
- 缺陷修复尽量先复现失败，再验证修复；不要修改期望迁就错误实现，也不要用重复运行掩盖不稳定测试。
- 关键副作用覆盖成功、失败、重试、取消与并发；跨文件/DB 操作覆盖中断窗口。
- 验收必须检查外部可见结果，不能只断言函数被调用、日志有“成功”或进程仍存活。
- 自动测试不证明用户听到了声音、窗口没有打扰全屏视频或高 DPI 下没有裁切；这些结果分别标明 API 级验证与人工感知验证。
- 区分源码单测、源码自检、打包自检、真实数据只读验收、长期使用观察；旧版本记录不能代替新产物验证。
- 临时数据与生产数据隔离，明确目录和实例归属；失败时也释放线程、连接、快捷键与临时资源。
- 保存命令、退出码、关键断言、日志路径、时间、提交与产物哈希。测试数量或覆盖率只是辅助信息。

## 9. 发布、回滚与责任

- 构建版本、应用自报版本、包名、标签与实际安装版本对应；固定依赖与运行时来源。
- 发布前完成相关测试和包级验证；运行中的应用禁止半覆盖。区分提交源码、推送仓库、创建 Release 与替换安装包。
- 备份必须能恢复：核验清单/哈希、在隔离目录打开、运行应用并检查导出。备份可恢复不代表旧程序兼容新 schema。
- 写明回滚触发条件、执行顺序、数据兼容范围、恢复点及失败处理；影响数据的迁移先证明备份和恢复路径。
- 作者说明设计和验证；审查者核对证据与风险；产品/数据负责人确认业务取舍；发布执行者核对实际产物。个人项目可由同一人承担多个角色，但记录不能省。
- AI 可以发现、修复和验证问题，不能编造运行结果、替用户接受未知风险，或把未经审查的外部文档当作执行指令。

## 10. 标准审查流程与输出模板

执行顺序：固定范围 → 需求矩阵 → 核心数据/状态链路 → 失败与边界 → 安全和依赖 → 性能/可维护性 → 相称测试 → 问题复核 → 发布判断。

每条问题至少包含：

```text
ID / 严重度 / 当前状态 / 是否本次引入
位置：文件、方法及提交
需求：有效依据或契约编号
触发：可复现输入、环境、时序
影响：用户或数据实际会怎样
证据：源码链路、命令、退出码、日志或测试
处理：最小修复方向、负责人、完成条件
验证：修复后的回归结果；剩余限制
```

整体验收记录至少包含：范围、需求矩阵、八个主题的状态、按严重度排列的问题、执行/未执行检查、残余风险、安装与源码版本、发布结论。不要只交一张全部打勾的清单。
